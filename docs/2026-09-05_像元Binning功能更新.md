# 2026-09-05 像元 Binning 功能更新

## 1. 更新目标

为大恒 `MER3-138-136G3M-P-SWIR` 高光谱相机增加像元 Binning 控制，并支持以下模式：

| Binning（X×Y） | 含义 |
|---|---|
| `1×1` | 不进行 Binning（全分辨率） |
| `1×2` | 垂直方向合并 2 个像元 |
| `2×1` | 水平方向合并 2 个像元 |
| `2×2` | 水平、垂直方向均合并 2 个像元 |

其中：

- **X**：水平方向，即图像宽度、空间像元方向、ENVI `samples`；
- **Y**：垂直方向，即图像高度、光谱波段方向、ENVI `bands`；
- 内部 numpy 图像 shape 统一表示为 **`(rows, cols)` = `(height, width)`**。

本次实施采用**相机 SDK 硬件 Binning**，不采用生产路径的软件缩小。

---

## 2. 相机 SDK 实现

真实相机通过 Daheng Galaxy SDK 的以下节点配置硬件 Binning：

```python
BinningHorizontal  # X，图像列/水平方向
BinningVertical    # Y，图像行/垂直方向
```

实现位置：

```text
src/device/daheng_device.py
```

### 行为说明

1. 仅允许在**停止采集**时设置 Binning；运行中切换会抛出错误。
2. 相机初始化时会应用保存的 Binning 设置。
3. 开始采集前会再次设置并读取回 Binning，避免相机状态被外部配置覆盖。
4. 每次设置后读取回：
   - `BinningHorizontal`
   - `BinningVertical`
   - `Width`
   - `Height`
5. `Width` / `Height` 是最终可信的实际输出尺寸；当 ROI 或固件功能联动时，不仅依赖理论计算结果。
6. 如果节点未实现、不可写、读回值不一致，或尺寸非法，设置会失败；中途失败时程序会尝试恢复先前模式。

### 预期满幅输出尺寸

| Binning | numpy shape（高×宽） | UI / 文件分辨率（宽×高） |
|---|---:|---:|
| `1×1` | `(1024, 1280)` | `1280×1024` |
| `1×2` | `(512, 1280)` | `1280×512` |
| `2×1` | `(1024, 640)` | `640×1024` |
| `2×2` | `(512, 640)` | `640×512` |

每个相机帧 metadata 新增以下字段：

```python
{
    "width": 640,
    "height": 512,
    "binning_x": 2,
    "binning_y": 2,
    "binning": "2x2",
    "original_width": 1280,
    "original_height": 1024,
}
```

## 3. Mock 相机模拟

实现位置：

```text
src/device/mock_device.py
```

MockDevice 已支持与真实相机相同的四种 Binning 模式和输出尺寸。

模拟方式：

1. 保留全分辨率 `1024×1280` 的模拟场景；
2. 依照当前 `(X, Y)` 对原始像元块进行平均；
3. 输出与真实硬件 Binning 相同尺寸的帧。

使用平均值而不是求和值，是为了在 Mock 模式中保持 Mono12 DN 范围，不出现不符合显示和存储约定的数值溢出。Mock 同样禁止采集中切换模式。

## 4. UI 更新

实现位置：

### UI 行为

- Binning 在以下状态不可修改：
  - 正在采集；
  - 正在录制；
  - 正在回放。
- 当前实际图像分辨率会更新显示。
- 选择 Binning 会保存至 `QSettings`；下次启动时程序尝试恢复该模式。
- 真实相机拒绝某个设置时，UI 会回退为相机实际确认的模式，并更新保存值。
- 切换后，下列坐标范围会根据新图像尺寸同步裁剪：
  - 光学校准 X/Y 坐标；
  - 四个光谱/空间曲线坐标；
  - 线扫显示的光谱行索引；
  - 当前选中像元坐标。
- 旧尺寸的显示帧缓存会在切换时清空，避免 UI 在新模式下短暂显示旧帧。
- 回放 binned 数据时，UI 也会依照文件中帧的实际 shape 自动调整坐标范围。

## 5. ENVI 和 Raw 存储更新

### 5.1 文件命名

保存文件名自动追加 Binning 和输出分辨率，示例：

```text
MTF-user-20260905_103000_Bin2x2_640x512.dat
MTF-user-20260905_103000_Bin2x2_640x512.hdr
MTF-user-20260905_103000_Bin2x2_640x512.json
```

格式为：

```text
<原会话名>_Bin<X>x<Y>_<宽>x<高>
```

这样可以防止不同 Binning 模式的数据文件混淆。

### 5.2 ENVI Header

实现位置：

```text
src/data/envi_writer.py
```

ENVI writer 不再固定写入 `samples=1280`、`bands=1024`，而是依据录制开始时相机实际输出尺寸写入。例如 `2×2`：

```text
ENVI
samples = 640
lines = <采集帧数>
bands = 512
data type = 12
interleave = bil
byte order = 0
binning horizontal = 2
binning vertical = 2
binning = 2x2
original samples = 1280
original bands = 1024
```

一个 ENVI 录制会话内必须保持相同的 `(bands, samples)`。如 Binning 发生变化，writer 会拒绝写入不同尺寸帧，因此必须先停止当前存储，再切换模式并开始新会话。

### 5.3 Raw JSON Sidecar

实现位置：

```text
src/data/raw_writer.py
```

Raw `.json` sidecar 在原有信息基础上新增：

```json
{
  "width": 640,
  "height": 512,
  "binning_x": 2,
  "binning_y": 2,
  "binning": "2x2",
  "original_width": 1280,
  "original_height": 1024
}
```

Raw writer 同样保持一个会话中所有帧尺寸一致。

## 6. NUC 与 Binning

实现位置：

```text
src/data/nuc.py
src/ui/main_window.py
```

当前数据流为：

```text
传感器采样
  → 相机内部硬件 Binning
  → SDK 输出 binned frame
  → 软件端 NUC
  → UI 显示 / Raw 存储 / ENVI 存储
```

因此，软件无法在硬件 Binning 之后回到原始 `1024×1280` 图像做 NUC。每个 Binning 模式必须使用单独标定的、尺寸严格匹配的 A/B 系数：

| Binning | NUC A/B 系数 shape |
|---|---:|
| `1×1` | `(1024, 1280)` |
| `1×2` | `(512, 1280)` |
| `2×1` | `(1024, 640)` |
| `2×2` | `(512, 640)` |

### NUC 安全机制

- 加载 NUC 时，A/B 文件按当前相机输出 shape 校验。
- `.npy`、`.csv` 文件保留并校验二维尺寸。
- 对平铺的 `.bin` / `.raw` 系数文件，按当前活动尺寸 reshape，避免 `1×2` 与 `2×1` 因元素数相同而出现歧义。
- 如果 Binning 切换后，已加载 NUC 系数与新帧 shape 不一致，软件会记录警告并**跳过 NUC**，原始 binned frame 继续正常显示和存储。

不建议将 `1×1` NUC 系数简单缩放用于其它 Binning 模式；应在每个 Binning 模式下独立完成平场/暗场标定。

## 9. 真实相机联调建议

在真实相机上按以下顺序确认：

1. 在停止采集状态下依次选择 `1×1`、`1×2`、`2×1`、`2×2`；
2. 检查日志中的 SDK 节点读回值与实际 `Width` / `Height`；
3. 检查单帧显示尺寸、光谱坐标和线扫索引范围；
4. 每种模式分别录制一段 ENVI 和 Raw 数据；
5. 核对文件名、ENVI `.hdr`、Raw `.json` 中的 Binning 与尺寸；
6. 分别加载每种模式对应的 NUC A/B 系数，确认匹配时生效、不匹配时被安全跳过。
